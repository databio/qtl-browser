# qtlstore v2

v1 stores two of `(nlp, beta, se)` and derives the third, differently per object kind. Every defect
found in the last two days came from that derivation rather than from any encoding:

| Found | What it actually was |
|---|---|
| `SIG_COLUMNS = ("p_perm", "p_beta")` | the format presumed a permutation pass, generalised from the two sources ingested, which both ran tensorQTL |
| `NLP_LIMIT = 300` fails a build | the inverse t's double range leaked into the *storage* rule; 4 of ARIC's 118 chr22 blocks trip it |
| `dof.at_edge` refuses a good fit | a guard written for a lower edge applied to an upper edge the search cannot widen past |
| slope error exceeds its own budget | 6.01e-03 against a 4.47e-03 ceiling on 4 of ARIC's 118 blocks, because the inverse t steepens as t^3 |
| `_vidx` crashes with no credible sets | an empty pandas slice loses its dtypes; blocked ARIC on every chromosome |
| GWAS lossless, QTL lossy | an exception the README had to document |

None of them was predicted. The common cause is that v1 encoded assumptions about the *shape of a
study* without recording them, so the first study with a different shape found them one at a time.
v2's job is to remove the derivation and, just as importantly, to **write down what it still
assumes** so the next surprise is a known risk rather than a discovery. That is the
[Possible gaps](#possible-gaps) section, and it is the part of this plan with the longest half-life.

## The schema

### The triple, 6 bytes a row, identical in all three object kinds

Stored **columnar** -- `nlp[n]`, then `beta[n]`, then `se[n]` -- not interleaved as v1's cis pair
array is. Three reasons, in order of weight:

1. **A partial read becomes possible.** The locus plot wants only `nlp`. Columnar means it can
   sub-range the first `2n` bytes of a block instead of all `6n`: 12.4 KB rather than 37.2 KB for a
   median 6,200-row phenotype -- *less than v1's 24.8 KB*. So the common read gets cheaper even
   though the block grows. **Hypothesis, to verify at step 3**; it depends on the browser issuing a
   sub-block range request, which it already does for variant catalog pages.
2. zstd compresses a column of similar values far better than a row of unlike ones, which matters
   for trans and GWAS where frames are compressed (cis blocks stay raw).
3. It is what trans and GWAS already do, so one layout rule covers all three.

| Field | Width | Code | Reserved |
|---|---|---|---|
| `nlp` | `u16` | `rint(-log10(p) / nlp_max * 65533)` | `65535` not tested, `65534` p underflowed in the source |
| `beta` | `i16` | `rint(beta / beta_max * 32766)` | `-32768` null |
| `se` | `u16` | `rint((ln se - lse_min) / (lse_max - lse_min) * 65534)` | `65535` null |

Four `f64` scales per scope -- `nlp_max`, `beta_max`, `lse_min`, `lse_max` -- where a scope is one
cis block, one trans frame, or one GWAS block. The slope sign lives in `beta`'s `i16`, which frees
bit 15 of the SE field, so `se` gets 16 bits where v1 gave it 15.

Each ruler is chosen for its quantity, and both choices are measured rather than assumed (ARIC
chr21/22, 170 blocks, within-block `max/min`):

- `se` spans a median factor of **5.2**, is strictly positive, and gets a **log** ruler: constant
  relative error, 1.3e-05 at 16 bits. The log ruler is also what makes `se` robust to a study whose
  per-variant sample size varies, where the span could be orders of magnitude instead of 5.
- `|beta|` spans a median factor of **28,264** and crosses zero, so no log ruler is available; a
  **linear** ruler against `beta_max` gives a half-step of `beta_max / 65,532`, so the error in units
  of a row's own SE is bounded by

  ```
  (beta_max / se_min) / 65,532
  ```

  **Not `z_max / 65,532`** -- an earlier draft of this plan said that and it was wrong by 3.6x on cis
  and 14x on GWAS. `beta_max` and `se_min` need not be the same row: a rare variant sets the largest
  effect while a common one sets the smallest standard error, so their ratio exceeds every single
  row's `|z|`. Verified against the probe:

  | scope | `z_max` worst | `beta_max/se_min` worst | bound | measured |
  |---|---|---|---|---|
  | TOPCHeF eQTL chr21, 186 blocks | 29.3 | **42.8** | 6.54e-04 | 6.35e-04 |
  | DCM GWAS chr1, 481 blocks of 2048 | 9.8 | **141.0** | 2.15e-03 | 1.81e-03 |

### Identity, unchanged

| | identity bytes | triple | total | v1 |
|---|---|---|---|---|
| cis `.qbe` | 0 -- a contiguous `vidx` run from `var_start` | 6 | **6** | 4 |
| trans `.qbt` | 12 (`u32` pos delta, `u32` rs, `u16` af, `u8` chrom ordinal, `u8` allele) | 6 | **18** | 16 |
| GWAS `.qbg` | 12 (same, `u8` n_code for the ordinal) | 6 | **18** | 21 |

The whole asymmetry is naming the variant. A cis row costs nothing to address because a block's rows
are a contiguous `vidx` run and the variant catalog supplies position and alleles by index. A trans
or GWAS row can be any variant, so it carries its own identity -- and that identity is 12 of its 18
bytes, two thirds of the row, against 6 for the statistics.

## Byte layouts

### cis results, kind 2, `.qbe` — one object per (phenotype type, chromosome)

```
[64-byte file header][block][block]...
```

One block per phenotype, found through the search index's `blk_off` / `blk_len`. Blocks are
**uncompressed** apart from the details frame, because a gene page range-reads one block and decodes
it with no inflate step.

Block, `72 + 6n + 12k + details_zlen`, padded to a multiple of 4:

| offset | type x count | field | v1 |
|---|---|---|---|
| 0 | `4s` | magic `QGB0` | same |
| 4 | `u32` | `blk_len` | same |
| 8 | `u32` | `n_rows` = n | same |
| 12 | `u32` | `var_start`, the first row's `vidx` | same |
| 16 | `u32` | **`flags`** | was `anchor` `i32`, dead since v1 (always 0) |
| 20 | `u32` | `pos_first` | same |
| 24 | `u32` | `pos_last` | same |
| 28 | `u32` | `n_cs` = k | same |
| 32 | `f64` | `nlp_max` | same |
| 40 | `f64` | `lse_min` | same |
| 48 | `f64` | `lse_max` | same |
| 56 | `f64` | **`beta_max`** | new |
| 64 | `u32` | `details_zlen` | same |
| 68 | `u32` | `details_len` | same |
| 72 | `u16` x n | `nlp` codes | was interleaved with se |
| 72 + 2n | `i16` x n | **`beta` codes** | new |
| 72 + 4n | `u16` x n | `se` codes, 16-bit, no sign | was 15-bit + sign |
| 72 + 6n | 12 x k | credible-set records: `u32 row, f32 pip, u8 cs_id, 3 pad` | same |
| 72 + 6n + 12k | zstd | details frame | same |

Header 64 -> 72 for `beta_max`; `anchor` becomes `flags`, which is where gap G1's future per-block
`i32` beta would be signalled. Measured cost of the header growth: 0.03 MB over 3,548 blocks.

### trans, kind 6, `.qbt` — one object per phenotype type, chromosome `all`

```
[64-byte file header][zstd frame][zstd frame]...
```

One frame per phenotype that has trans rows, located by the search index's `trans_off` /
`trans_len`; a gene's frames are one contiguous range. Each frame is zstd over a columnar payload.

Frame payload, `48 + 18n + heap_len`:

| offset | type x count | field | v1 |
|---|---|---|---|
| 0 | `4s` | magic | same |
| 4 | `u32` | `n` rows | same |
| 8 | `f64` | `nlp_max` | same |
| 16 | `f64` | `beta_max` | same |
| 24 | `f64` | **`lse_min`** | new |
| 32 | `f64` | **`lse_max`** | new |
| 40 | `u32` | `heap_len` | same |
| 44 | `u32` | reserved, 0 | same |
| 48 | `u32` x n | position delta: absolute on the first row of a chromosome, else from the row before | same |
| 48 + 4n | `u32` x n | `rs_number`, 0 = none | same |
| 48 + 8n | `u16` x n | `af` code | same |
| 48 + 10n | `u16` x n | `nlp` codes | same |
| 48 + 12n | `i16` x n | `beta` codes | same |
| 48 + 14n | `u16` x n | **`se` codes** | new -- v1 derived se from `|beta| / t(nlp, dof)` |
| 48 + 16n | `u8` x n | chromosome ordinal, 1..255 in catalog table order | same |
| 48 + 17n | `u8` x n | allele code, 0 = heap | same |
| 48 + 18n | heap | `ref \t alt \n` per code-0 row | same |

Header 32 -> 48 for the two SE scales. Row 16 -> 18.

### GWAS, kind 4, `.qbg` + index kind 5, `.qgi`

This is the one that needs explaining, because it is the only kind that compresses genome-wide and
is read by position rather than by phenotype.

**One `.qbg` per chromosome** (22 in the live store), and **one `.qgi` for the whole GWAS**:

```
.qbg   [64-byte file header][zstd block][zstd block]...     back to back, no padding
.qgi   [64-byte file header][one zstd frame]
```

A `.qbg` block is **B = 2048 consecutive rows** sorted by `(pos, ref, alt, rs_number, p, n, beta)`,
each block its own zstd frame. Block payload, `40 + 18n + heap_len`:

| offset | type x count | field | v1 |
|---|---|---|---|
| 0 | `u32` | `n` rows | same |
| 4 | `u32` | `heap_len` | same |
| 8 | `f64` | **`nlp_max`** | new |
| 16 | `f64` | **`beta_max`** | new |
| 24 | `f64` | **`lse_min`** | new |
| 32 | `f64` | **`lse_max`** | new |
| 40 | `u32` x n | position delta: first absolute, then `pos[i] - pos[i-1]` | same |
| 40 + 4n | `u32` x n | `rs_number`, 0 = none | same |
| 40 + 8n | `u16` x n | `af` code | was `rint(af * 1e4)`, now `rint(af * 65534)` (D8) |
| 40 + 10n | `u16` x n | `nlp` codes | **was `u16 p_mant` + `i8 p_exp`, 3 bytes** |
| 40 + 12n | `i16` x n | `beta` codes | **was `i32` = `rint(beta * 1e4)`, 4 bytes** |
| 40 + 14n | `u16` x n | `se` codes | was `rint(se * 1e4)`, same width, different meaning |
| 40 + 16n | `u8` x n | `n_code`, index into the index's n table | same |
| 40 + 17n | `u8` x n | allele code, 0 = heap | same |
| 40 + 18n | heap | `ref \t alt \n` per code-0 row | same |

Payload header 8 -> 40 for the four scales; row 21 -> 18. At B = 2048 the **uncompressed** block
payload goes 43,016 -> 36,904 bytes, −14.2%: the 32 bytes of scales are paid once per 2,048 rows and
the 3 bytes saved per row more than cover them.

The **stored** object is slightly larger, not smaller. Measured on the DCM GWAS, chr21/22, the same
349,950 rows: v1 13.290 B/row, v2 13.585, **+2.2%**. v1's `rint(x * 1e4)` leaves structure that zstd
finds; quantized codes spread their entropy over all 16 bits, which costs more than the three bytes
saved. Uniformity is the reason to do it; size is not.

**How a genome-wide window is read.** The `.qgi` payload carries, per chromosome in catalog table
order: an 8-byte name, `n_blocks`, then `first_position[n_blocks]` and `end_offset[n_blocks]` -- the
byte after each block in that chromosome's `.qbg`. Block 0 starts at byte 64, and block *k* spans
`end_offset[k-1] .. end_offset[k] - 1`. So for rows with `lo <= pos <= hi`
(`packfmt_v1.gwas_window`):

1. `end` = the last block whose `first_position <= hi`; none means no rows.
2. `start` = the last block whose `first_position < lo`, else 0. The strict `<` is deliberate: it
   covers a position repeated across a block boundary.
3. Fetch `(start == 0 ? 64 : end_offset[start-1]) .. end_offset[end] - 1` in **one** range request,
   inflate blocks `start..end`, keep rows inside the window.

That is the whole genome-wide story: the index is small enough to hold in memory (one `.qgi`, 0.00
MB in the live store), it answers "which bytes" without touching a block, and a locus is one HTTP
range read of a few blocks. v2 changes none of this: same B, same index, same window rule, and the
block a reader fetches is within a couple of percent of the size it was.

The **bin summary** is separate and unchanged: `gwas.bins` names a small `.arrow.zst` holding the
strongest p per 5 Mb window, so the landing page's genome track never reads a block at all.

### Size, all three kinds together

Per-row and per-scope, verified by re-deriving every offset:

Uncompressed row widths, and the scope overhead each pays once:

| | scope | v1 row | v2 row | scope overhead v1 -> v2 | per-row effect |
|---|---|---|---|---|---|
| cis `.qbe` | one phenotype, ~6,200 rows | 4 | **6** | 64 -> 72 B block header | **+50%** |
| trans `.qbt` | one phenotype | 16 | **18** | 32 -> 48 B frame header | +12.5% |
| GWAS `.qbg` | 2,048 rows | 21 | **18** | 8 -> 40 B payload header | −14.2% |

The four `f64` scales cost 32 bytes a scope, which is 0.0156 B/row at the GWAS block size and
nothing at all against a cis phenotype's thousands of rows.

**Stored** bytes, both stores built genome-wide from the same contract tables
(`pipeline/build_store.py`, 2026-10-07), each `validate` clean:

| | rows | v1 | v2 | |
|---|---|---:|---:|---|
| `.qbe` cis | 623,057,691 | 2,415.6 MB | 3,604.7 MB | **+49.2%** |
| `.qbt` trans | 15,824,574 | 188.5 MB | 212.5 MB | +12.7% |
| `.qbg` + `.qgi` GWAS | 12,494,731 | 158.4 MB¹ | 163.2 MB | +3.1% |
| everything else² | | 332.5 MB | 332.5 MB | — |
| **store, GWAS excluded from both** | | **2,937 MB** | **4,150 MB** | **+41.3%** |

¹ the genome-wide v1 store holds no GWAS (`gwas.parquet` was absent from the tables directory when
it was built), so this is the measured v1 rate of 13.290 B/row from the chr21/22 build applied to
the same rows. ² hits, variant catalog, rsID index, gene lookup, Arrow search index — byte-identical
between the two, as `which_codec` reports them codec-independent.

`.qbe` dominates because 98.4% of a results object is the row array -- measured, not assumed:
2,415.6 MB over 623,057,691 rows is 4.065 B/row against a 4 B/row payload, so headers and details
frames are 0.065 B/row between them. v2 is 6.067 B/row against 6.

So the stored cost of the triple is **+49.2% where the triple is**, and +41.3% over a store whose
other 11% is already version-independent. The earlier +38% projection assumed a smaller `.qbe`
share than a genome-wide build actually has.

### The `precision` block, one shape for all three kinds

v1's precision reporting is inconsistent in three ways: it calls the same quantity `slope_*` on the
cis side and `beta_*` on the trans side, it reports that quantity in units of SE for cis and in
absolute effect units for trans (so the two cannot be compared to each other or to the budget), and
it mixes computed ceilings with an actual measurement under names that do not say which is which.
GWAS has no precision block at all, because v1's GWAS is lossless.

v2 uses one block, same keys, in every results set, every trans entry and every GWAS object:

```json
"precision": {
  "theoretical_limit": { "neglog10p": 1.269e-03, "beta_over_se": 6.54e-04,
                         "se_rel": 2.34e-05, "af": 7.63e-06 },
  "measured_worst":    { "neglog10p": 1.81e-04, "beta_over_se": 6.35e-04,
                         "se_rel": 1.12e-05, "rows_compared": 123458053 }
}
```

- **`theoretical_limit`** is half a quantization step in each quantity's own unit, computed from the
  **four header scales and nothing else** -- no row decoded, no source value consulted. So any
  reader recomputes it from a stored block, which is what makes it a property of the format rather
  than of a build, and it holds for every row including rows a later build would write.
  `beta_over_se` divides the absolute half-step by `se_min = exp(lse_min)`, the smallest stored
  standard error, because the step is absolute and the row it hurts most is generally not the row
  that set `beta_max`.
- **`measured_worst`** is found by decoding every row and comparing against the source values the
  adapter supplied, with `rows_compared` as the n. Both names say "extreme" on purpose: every entry
  is a maximum, and `measured` alone would read as a typical error.

The unit is in each name: `_over_se` is in units of the row's own standard error (the denomination
of SPEC's 4.47e-03 budget), `_rel` is relative, a bare name is absolute in the quantity's own units.

**`measured_worst` exceeding `theoretical_limit` is a detectable defect** -- the arithmetic says it cannot
happen, so if it does, the encoder or the scales are wrong. `scan_codes` asserts it (step 4).

Mapping from v1:

| v1 | v2 | why |
|---|---|---|
| `neglog10p_max_error` | `theoretical_limit.neglog10p` | same meaning, now labelled as a ceiling |
| `slope_se_max_rel_error` | `theoretical_limit.se_rel` | `slope_` named the wrong quantity; it is the SE's error |
| `slope_max_error_over_se` | `measured_worst.beta_over_se` | always a measurement, never a ceiling |
| `slope_rows_compared` | `measured_worst.rows_compared` | a count, not an error |
| `af_max_error` | `theoretical_limit.af` | same; improves to 7.63e-06 under D8, from 5.0e-05 on the GWAS side |
| trans `beta_max_error` | `theoretical_limit.beta_over_se` | **restated in SE units**, so it is comparable to cis and to the budget |
| — | `theoretical_limit.se_rel` on trans | trans had **no** SE error figure, despite SE being its one reconstructed value |
| — | the whole block on GWAS | v1 has none |
| — | `measured_worst.*` for all three quantities | v1 measured only the rebuilt slope |

Dropping `slope_` finishes a rename the UI already made in PR #3; the pipeline is the last place
using tensorQTL's column name for what `CONTRACT.md` calls `beta`.

`measured_worst` gains `neglog10p` and `se_rel` because in v2 the builder holds `p`, `beta` and `se` at
the moment it encodes and already decodes blocks back to compute the slope error -- extending that
to all three is nearly free, and it shows when a ceiling is loose. It is tight on TOPCHeF eQTL
(6.54e-04 against 6.35e-04) and loose on GWAS chr1 (2.15e-03 against 1.81e-03), which is
only visible with both numbers side by side.

was published in every store, under a name that did not invite comparison with anything.

|---|---|---|---|
| D1 | Store the triple everywhere; derive nothing | user-owned, decided 2026-10-07 | Removes every failure in the table above. Forces +38% store and +49% on the cis read path, which is what a gene page range-reads. |
| D2 | GWAS joins the quantized triple and stops being lossless | user-owned, decided 2026-10-07 | The README already states the principle; GWAS was its exception. Forces the loss of `gwas_scaled`'s build-time refusal of over-precise input, replaced by D3. |
| D3 | One `precision` block shape for all three kinds, `theoretical_limit` + `measured_worst` | AI-owned, defended | GWAS gains one at all (the honest replacement for the lost losslessness guard); cis and trans get consistent names and comparable units. `theoretical_limit` rather than `bound`/`allowed`/`guaranteed`: it states both that the number is computed and that nothing exceeds it, and it makes `measured_worst > theoretical_limit` read as the detectable defect it is rather than as a broken promise. |
| D4 | `beta` is `i16`, `se` keeps the log ruler and takes the freed sign bit | AI-owned, defended | Measured. `i32` beta would double the cost of the triple's largest field to buy precision nothing needs, and the bound `z_max/65,532` is inside budget up to |t| = 293 (gap G1). |
| D5 | `FORMAT_VERSION` 1 -> 2, full re-upload | AI-owned, defended | The layout changes in all three object kinds, and the version byte is in every object header (`qtlstore.py:78`). Flagging the layout in the dead `anchor` `i32` instead would save only the 18% of bytes that are not `.qbe`/`.qbt`/`.qbg` and would leave an old reader silently misreading the pair array at the wrong stride. |
| D6 | The triple's internal agreement is **recorded, not enforced** | AI-owned, defended -- **reverses an earlier call** | `2026-10-07-unified-schema.md` D4 proposed asserting that `beta/se` agrees with `t(nlp, dof)`. So `scan_codes` reports the worst disagreement per results set and `precision` stores it; nothing fails on it. Measured today: 2.4e-03 (eQTL), 4.0e-03 (sQTL), 2.2e-02 (ARIC), in absolute |t|. |
| D7 | `dof` becomes provenance | AI-owned, defended | Still fitted, still recorded in the experiment pointer, still wanted by `verify_v0`; nothing decodes through it. A null dof stops costing an experiment its effect sizes. |
| D8 | `af` unified to `rint(af * 65534)` everywhere | AI-owned, default | The catalog uses `x65534` and GWAS `x1e4`; free to align while the layout changes. Challenge if 4-decimal af matters anywhere. |
| D9 | v2 is built and compared locally before anything is uploaded | user-owned, decided 2026-10-07 | A local TOPCHeF v1 build exists and validates; v2 gets the same treatment, object for object, before the bucket or either app is touched. |
| D10 | Gaps are recorded in this plan, not fixed speculatively | AI-owned, defended | Each gap below names the assumption, what breaks it, and how it would present. Fixing a gap no dataset has hit yet costs bytes on every row. The point is that the next one is looked up, not discovered. |

## Possible gaps

v1 had no section like this, which is why its assumptions were found by collision. Each entry is an
assumption v2 **still** makes. "Breaks it" means a real study design or a real tool, not a
hypothetical. Severity is about what a reader would see, not about likelihood.

### G1 — a block whose `beta_max / se_min` exceeds 293

- **Assumption**: the `i16` beta's error, `(beta_max / se_min) / 65,532` in SE units, stays inside
  the 4.47e-03 slope budget. The budget is reached at a ratio of **293**.
- **Correction worth keeping**: an earlier draft stated the bound as `z_max / 65,532` and set the
  threshold at `|t| > 293`. That is wrong, and optimistically so. `beta_max` and `se_min` are
  generally **different rows** -- a rare variant carries the largest effect, a common one the
  smallest standard error -- so the ratio runs well above any row's own `|z|`. Measured:

  | scope | `z_max` worst | `beta_max/se_min` worst | share of budget |
  |---|---|---|---|
  | TOPCHeF eQTL chr21 | 29.3 | 42.8 | 15% |
  | ARIC EA chr22 | 85.7 | ~98 | 34% |
  | **DCM GWAS chr1, blocks of 2048** | 9.8 | **141.0** | **48%** |

- **Breaks it**: the **GWAS side is closest**, not the QTL side, which is the opposite of what the
  `z_max` framing implied. A GWAS block is 2,048 consecutive positions rather than one phenotype, so
  it mixes rare variants (large beta, large se) with common ones (small se) and the ratio is driven
  by that spread, not by signal strength. A larger or more deeply imputed GWAS -- more rare variants
  per 2,048 rows -- pushes it further. On the QTL side, a much larger cohort does it: |t| grows as
  sqrt(n), so n = 50,000 against ARIC's 7,213 roughly doubles the ratio to ~250. **Inference from
  scaling for the QTL case; measured for the GWAS case.**
- **Presents as**: a stated error bound quietly larger than the budget SPEC documents. No crash,
  nothing visibly wrong.
- **If it happens**: for GWAS, the cheapest lever is **B**, the rows per block -- it is already a
  tunable header field, and a smaller block narrows the variant mix and therefore the ratio, at the
  cost of more blocks and a larger `.qgi`. For cis, a per-block `i32` beta signalled in the new
  `flags` field. Do not raise `BETA_MAXQ` globally; that spends 2 bytes on every row of every study
  to serve a few blocks.

### G2 — a source whose p, beta and se are not related by a Student t

- **Assumption**: none, for *storage* -- and that is the point. v1 **required** the relation,
  because it reconstructed beta through it. v2 does not, which is its largest robustness gain and
  the one hardest to see from the diff.
- **Breaks the old assumption**: SAIGE (saddlepoint approximation), REGENIE and fastGWA (approximate
  firth / LOCO), Firth logistic regression, score tests, permutation-only outputs, and any
  normal-approximation pipeline. Also any binary-trait QTL where beta is a log odds ratio.
- **Presents as**: under v1, a dof fit with a large residual, so `dof: null`, so **no effect sizes at
  all** for the experiment. Under v2, nothing -- the triple is stored as published.
- **Consequence**: the consistency record (D6) will show large disagreement for such a source, which
  is correct behaviour and must not be treated as corruption. The `precision` block should carry the
  dof fit's `usable` flag alongside, so a reader can tell "t-consistent" from "not expected to be".

### G3 — phenotypes in the millions

- **Assumption**: one block and one search-index row per phenotype is affordable. TOPCHeF has
  100,226 phenotypes; the local chr21/22 subset has 3,548 blocks and 0.23 MB of block headers.
- **Breaks it**: mQTL. An EPIC array is ~865,000 CpGs and a WGBS study is millions. Single-cell
  eQTL multiplies genes by cell types -- 20,000 x 14 is 280,000 phenotypes per study. caQTL on peaks
  is ~150,000-500,000.
- **Presents as**: block headers alone at 64 B x 1e6 = 64 MB per results set, a search index with a
  row per phenotype that the browser reads whole per chromosome, and a `.qbh` hits file whose `ord`
  column stops compressing. The format does not break; the **browser's startup cost** does.
- **If it happens**: the search index already splits by chromosome; it would need splitting by
  phenotype range too, and the gene page would need a phenotype-level index rather than a
  per-chromosome scan. Worth noting that `MAX_PAGE_RECORDS = 65535` and `cs_id <= 127` are unrelated
  and fine; the pressure is on the index, not the codes.

### G4 — per-variant sample size on the QTL side

- **Assumption**: one `n` per experiment. `CONTRACT.md`'s `nominal` has no `n` column at all, and
  `n_samples` lives in the ingestion report and the dof fit.
- **Breaks it**: any QTL meta-analysis, and any study with per-variant missingness reported. The
  GWAS side already needed this and has `n_code` -- a `u8` into a table of **at most 255 distinct
  n values** (`GWAS_MAX_N_VALUES`). A per-variant-N meta-analysis has thousands of distinct values,
  so the GWAS side's own encoding breaks there too.
- **Presents as**: an adapter with nowhere to put the number, so it is dropped; and for the GWAS
  side, `gwas_codes` raising on the n table. Silent on the QTL side, loud on the GWAS side.
- **If it happens**: an optional per-row `n` field, or an `n` quantized like `se` against a per-scope
  range. Note that this is the one gap where v2 is **no better than v1** -- the triple does not
  include n, and coloc's `sdY` estimation wants it (see G8).

### G5 — alleles that are not short ASCII strings

- **Assumption**: a site is `(chr, pos, ref, alt)` with both alleles short upper-case ASCII; 12
  common SNP pairs get a `u8` code and the rest go in a tab-separated heap.
- **Breaks it**: structural variants. A 10 kb deletion's ALT as a literal string puts 10 kB in the
  allele heap for one row; symbolic alleles (`<DEL>`, `<INS:ME>`) are not representable as a REF/ALT
  pair the refcheck can verify at all. Also VCF-style `*` for a spanning deletion.
- **Presents as**: a heap that dwarfs the frame, or an adapter that cannot produce a `sites` row and
  drops the variant -- which `CONTRACT.md` already requires it to count, so at least it is visible.
- **If it happens**: out of scope for a QTL store as designed. Worth saying so explicitly rather
  than leaving it implied, because "variant" reads as including SVs to most people.

### G6 — more than one assembly in a store

- **Assumption**: one store, one refget collection. Every catalog is checked against it and the
  overlap index spans catalogs on that basis.
- **Breaks it**: already happened. MESA's cis-eQTL release is **GRCh37**, which is why it is deferred
  in `2026-10-06-pqtl-sources.md` (D22). Anything pre-2019 is GRCh37; mouse and other species are
  their own collections.
- **Presents as**: either two disjoint coordinate universes with no cross-catalog overlap -- which
  defeats the point of one store -- or a liftover the format cannot verify.
- **If it happens**: re-anchor by variant identity through dbSNP rather than lifting coordinates,
  then refcheck against GRCh38 as usual. The format needs no change; the adapter does.

### G7 — a phenotype that is not on one chromosome, or not anywhere

- **Assumption**: a cis block's rows are a contiguous `vidx` run on one chromosome, which is what
  makes a cis row cost 4 (now 6) bytes instead of 18.
- **Breaks it**: a trans-dominant design where the "cis window" is meaningless; fusion genes and
  readthrough transcripts spanning two chromosomes; phenotypes with no genomic location at all
  (metabolite ratios, cell-composition traits, protein ratios).
- **Presents as**: already handled at the edges -- `chr` is nullable in the search index for a
  trans-only phenotype, and `gene_id` is nullable. The real cost is that such a phenotype gets no
  cis block and so no locus view, which is a UI gap rather than a format one.

### G8 — coloc's priors and trait scale

- **Assumption**: `coloc.abf`'s `W1 = 0.15^2` means "a prior SD of 0.15 **trait standard
  deviations** per allele", so beta must be reported per trait SD -- `sdY = 1`. This is a real
  assumption, not a convention: in `logAbf` the shrinkage is `r = W/(W + se^2)`, and rescaling the
  trait by `c` sends `se^2 -> c^2 se^2` while `W` stays fixed, so the Bayes factor moves on
  identical data. Nothing in the experiment pointer records the scale.
- **Measured, 2026-10-07**: the three results sets in hand are all effectively `sdY = 1` on their
  reported scale, so **today's priors are right and no coloc number is currently mis-scaled.**
  tensorQTL inverse-normal-transforms expression, and ARIC's phenotypes were pre-residualised and
  standardised before PLINK2 (`sdY` estimate 0.9990 with only 2 model parameters, where the
  estimator is unbiased).
- **The trap, and it is the reason this entry exists**: coloc's own `sdY.est`
  (`sqrt(median(se^2 * N * 2af(1-af)))`) recovers the **residual** SD, which equals the trait SD only
  when the source fitted no covariates. Applied to our data it returns 0.5639 (TOPCHeF eQTL, 81
  model parameters), 0.9653 (sQTL, 36) and 0.9990 (ARIC, 2) -- those are `sqrt(1 - R^2)` for the
  variance each model's covariates absorbed, and they **independently reproduce the covariate counts
  the dof fit found by a different route**. "Fixing" the prior with that estimate would shrink
  TOPCHeF's eQTL `W` from 0.0225 to 0.00716 and make the coloc **3x wrong in the name of
  correctness**. 70 expression PCs violate the small-variance-explained premise `sdY.est` rests on.
- **Breaks the assumption for real**: a source that does not standardise. A methylation
  beta-value in [0,1], a metabolite ratio, an untransformed protein concentration, or a raw
  expression count would have `sdY` genuinely far from 1 and would silently inherit `0.15^2`.
- **Presents as**: posteriors wrong in a direction nobody can see, because PP.H4 looks like a
  probability either way. Still the only gap here that yields a confidently wrong *scientific*
  number rather than a crash, a size problem or a missing feature -- but latent rather than active.
- **Decided 2026-10-07: documented, not declared.** A `phenotype_scale` / `sdY` field was designed
  and then dropped. Every scale the store could represent without a per-phenotype escape hatch
  (`inverse_normal`, `standardised`) means `sdY = 1`, so the field could only ever hold `1.0` and the
  multiplication in the reader would always be a no-op -- ceremony that prevents nothing. `n_samples`
  went the same way: it would be a second field existing only to feed an estimator we have decided
  not to use.
- **So the assumption is written where it will be read**: the `AbfPriors` docstring in
  `coloc-abf.ts` (for whoever maintains the prior) and the About page's Colocalization entry (for
  whoever interprets a PP.H4), both with the measured numbers and the `sdY.est` trap. That *is* the
  fix -- v1's six accidental discoveries came from unwritten assumptions, not from missing fields.
- **The day a raw-scale source arrives**, the choice is explicit rather than silent: give the format
  a per-phenotype scale, or refuse the source. Do not add an automatic `sdY.est` fallback; it is
  wrong for any study with covariates, which is nearly all of them.
- Supersedes `2026-10-06-pqtl-sources.md` D16.

### G9 — nlp resolution at extreme magnitudes

- **Assumption**: a `u16` code against an `f64 nlp_max` is enough resolution at any magnitude.
  Deleting `NLP_LIMIT` makes `nlp_max` unbounded.
- **Checked**: resolution is `nlp_max / 65,533`, so at `nlp_max = 10,000` the step is 0.15 in
  -log10 p. Since `z ~ sqrt(2 ln10 * nlp)`, that is `dz ~ 0.0016` at `z ~ 214` -- negligible. The
  encoding degrades gracefully, unlike the `i16` beta (G1).
- **Presents as**: nothing. Recorded so it is not re-litigated.

### G10 — the store as an archive

- **Assumption**: the store is a *view*; exact values live in the source releases. v2 makes this
  uniform by rounding the GWAS side too (D2).
- **Breaks it**: anyone who wants to run a fresh meta-analysis or fine-mapping *from* the store
  rather than from the sources. v1 could serve that for the GWAS side; v2 cannot for anything.
- **Presents as**: a user computing something slightly different from what the authors published,
  with no error message.
- **If it happens**: the `precision` block is the mitigation, and it must stay prominent in the
  README and About page rather than only in SPEC.

## What this changes elsewhere

- **`packfmt_v2.py`** (new, beside v1 which `verify_v0` still needs): `quantize_beta`, a 16-bit
  `quantize_se`, the three encoders and decoders, headers grown for `beta_max` (+8 B/block, measured
  at 0.03 MB over 3,548 blocks).
- **Builders**: `results.py` encodes beta and drops `slope_err`; `gwas.py` drops the lossless
  enforcement and gains `precision`.
- **Reader**: `store-decode.ts` loses `tFromNlp` from the hot path, `transSe` entirely, and the
  `dof === null` branches; `coloc-abf` reads `z = beta/se` on both sides.
- **`scan_codes.py`**: beta's reserved code, and the advisory consistency sweep (D6).
- **`dof.py`**: unchanged in behaviour, demoted in role (D7).
- **`verify_v0.py`**: compares v0 against v1 and will need the v2 path, or pinning to v1.
- **`bench_store.py`**: the natural home for the v1-vs-v2 object comparison.
- **SPEC.md** sections 8, 9, 10, 13 and the v0/v1 delta table; **README**'s rounding sentence.
- **`CONTRACT.md` is unaffected.** Adapter tables already carry `beta`, `se` and `pvalue` per row,
  which is why no adapter changes -- the whole reason this is possible at all.

### D5 as built

`FORMAT_VERSION` is a parameter of `qs.file_header` with `SUPPORTED_VERSIONS = (1, 2)`, threaded
from the codec in `results.py`/`gwas.py` and as an explicit `version=` in the codec-free builders
(`catalog.py`, `annotation.py`, `overlap.py`). Two things were added that the plan did not call for
and that the build needed:

- **`Store.validate` compares every object header to `store.json`'s `format_version`.** Nothing did
  before, which is why two v1 trans objects sat in a v2 store and validate passed. `qtlstore.py`
  gained `codec_for(version)`, the one place both codecs are named.
- **`pipeline/build_store.py`**, because there was no store build driver at all: the three builder
  CLIs were run by hand and nothing called `write_store`, so `store-genome-v1` was built with no
  `store.json` and could not be validated — the exact check that catches a mixed store.

Three defects found in the process, all of them invisible in a diff:

1. `build_trans` called the v1 encoder inside a v2 store, and the trans SQL never selected `t.se`
   (v1's encoder has no `se` parameter, so nothing asked for the column).
2. v2's `decode_gwas_block` returned `n` as the row count where v1 returns it as the sample size.
   `read_window` indexed a scalar and raised; had the names merely been swapped in meaning it would
   have returned plausible wrong numbers.
3. v2's trans magic was `QGT2`, one character from v1's `QTT2` in a non-version position. Now `QTT3`.

`test_qtlstore.codecs_do_not_mix` now asserts the rule that would have caught (1): a builder imports
`packfmt_v1` only, and takes v2 as a parameter or not at all.

### Step 4

`scan_codes.py` reads both layouts, picking the codec from each object's own file header rather than
being told — reading a v2 block at the v1 layout would not raise, it would count beta codes as SE
codes and report a store full of reserved values. Added `beta_null`, the two new scale rules, and
the `measured_worst <= theoretical_limit` check over the pointer's precision blocks.

A limit of 0.0 means *not stated*, not a limit of zero, so it prints `NO LIMIT STATED` with the
measured figure rather than counting as a pass. On the chr21/22 stores: v1 has four such
measurements, one of them the figure at 99.9% of its budget; v2 has none.

The advisory consistency record (D6) is not done.
